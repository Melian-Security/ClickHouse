# Benchmark kits for the melian/fix-* branches

These kits produced the numbers quoted in the fork PRs. They are kept here, off the PR
branches, so the PRs carry only the change and its upstream-style tests. Each directory has a
synthetic data generator (`gen.py`) and an A/B driver that alternates a base and a fix binary.

| kit | branch | measures |
|---|---|---|
| `json-merge/` | melian/fix-json-merge | One `OPTIMIZE ... FINAL` merge of many parts with a wide JSON column (`advanced` shared data, `map_with_buckets` zero-level parts). Merge duration and user CPU from `system.part_log`, compact and wide parts; `profile.sh` records a system-wide perf profile of the merge. |
| `path-resolve/` | melian/fix-path-resolve | Single-threaded parse of JSON text into a JSON column with typed paths and `max_dynamic_paths=64` (`FORMAT Null`), and a single-threaded MergeTree insert. |
| `surrogates/` | melian/fix-surrogates | Parse and MergeTree insert throughput on clean data (checks the surrogate fallback costs nothing); `repro.sh` reproduces the unpaired-surrogate parse error. |
| `key-strings/` | melian/fix-key-strings | Single-threaded `JSONAsObject` parse into a JSON column, user CPU of `clickhouse local`; then compares the MergeTree parts written by both binaries byte for byte. |
| `dupkey/` | melian/fix-dupkey | JSON-type parsing (parallel and single-thread) and MergeTree insert, wall and CPU time. |
| `issue-93976/` | melian/fix-issue-93976 | PREWHERE ordering of `activity_id = 12 AND <JSON path> = ...` on compact and wide parts: `repro.sh` prints the chosen order and ReadCompressedBytes per binary, `ab.sh` / `ab_server.sh` alternate base and fix (`ab_server.sh` reads `query_duration_ms` from `query_log`), `minimal.sql` is the upstream-issue reproducer, `alter_repro.sh` checks the ALTER-to-v3-serialization report from the same issue. |
| `insert-collapse/` | melian/fix-insert-collapse | Server CPU of inserts into `ReplacingMergeTree` with a wide JSON column, `optimize_on_insert` 0 and 1, unique and duplicate keys; `run_all.sh` drives the matrix and `summarize.py` prints medians. |
| `shared-data-read/` | melian/fix-shared-data-read | Cold reads of a wide JSON column (`advanced` shared data, 32 buckets, Wide parts) from an S3 disk backed by a MinIO container with `tc netem` latency on the docker bridge: sub-object (`event.^unmapped`) point lookups and ranges, shared-data paths, whole `event`, `JSONAllPaths`. `bench.sh setup` loads the data, `run` alternates base and fix with all caches dropped before each query and summarises `query_log` (duration, S3 GETs, prefetches, marks wait), `check` compares query results. |
| `shared-data-write/` | melian/fix-shared-data-write | One Vertical `OPTIMIZE ... FINAL` merge of 8 Wide parts (250K rows each, the production `event` type, `advanced` shared data with 32 buckets): merge duration, user CPU and real time from `system.part_log`, 5 alternating base/fix runs on pinned cores, and the md5 of every file of each merged part (must match across all runs and binaries). `bench.sh load` builds the source parts once with the base binary and clones them for the fix server, `run` alternates, `prof` runs the server under `perf record` and reports the merge thread's inclusive and self profile. |
| `shared-data-gather/` | melian/fix-shared-data-gather | The gather step of one Vertical `OPTIMIZE ... FINAL` merge of 8 Wide parts (1M rows each, the production `event` type, `advanced` shared data, rows of all parts interleaved by `ts`), so `ColumnObject::insertFrom`/`insertRangeFrom` move values between dynamic paths and shared data per source part. Same driver as `shared-data-write/` (`load`, `run`, `prof`), pinned to cores 8-15 by default; `GEN_DIR` loads `part_<i>.jsonl` files generated beforehand in parallel. Background merges stay off (`max_bytes_to_merge_*=1`), only the `OPTIMIZE` merges. |
| `dynamic-serialization/` | melian/fix-dynamic-serialization | Server CPU of concurrent `INSERT ... FORMAT JSONEachRow` over HTTP (the server parses the JSON; `CONC` inserts at once) into the production `event` type with ~300 distinct paths overflowing into shared data (arrays of objects and of strings, date-time strings), then CPU of `OPTIMIZE ... FINAL`; `run.sh` takes an optional `perf record` prefix, `ab.sh` alternates two binaries and `summarize.py` prints medians and content hashes. `micro.sh` runs the queries of the PR's perf test. |
| `zstd-context/` | melian/fix-zstd-context | One Vertical `OPTIMIZE ... FINAL` merge of 3 Wide parts (the `json-merge` schema and data, `python3 ../json-merge/gen.py DATA 128`) after a concurrent HTTP insert pass, per memory-worker mode (`default`, and `poc` = `memory_worker_purge_total_memory_threshold_ratio=0.001`, which keeps jemalloc `dirty_decay_ms` at 0), alternating base and fix on pinned cores: merge duration and user/system CPU from `system.part_log`, insert CPU, merge-thread `trace_log` samples in `madvise` / `ZSTD_freeCCtx`, and the md5 of every file of each merged part. `summarize.py results.tsv` prints medians and the change. |
| `merge-stream-cache/` | melian/fix-merge-stream-cache | One Vertical `OPTIMIZE ... FINAL` merge of 8 Wide parts (1M rows each) with the production-shaped JSON column, servers pinned with `taskset` (default cores 0-7). `ab.sh setup` inserts one part per generated file, `run` alternates base and fix and prints median/min/max of merge wall and user CPU from `system.part_log`, `check` compares every file of the merged parts byte for byte, `profile` records a perf profile of one merge. |
| `parallel-vertical-merge/` | melian/fix-parallel-vertical-merge | One Vertical `OPTIMIZE ... FINAL` merge of 8 Wide parts (250K rows each, 2M rows, 5 GiB) of a table with the production `event` JSON type, a `raw` String, a `Map(String, Dynamic)` and ~25 ordinary columns derived from the event (`load.sql`; rows from `python3 ../merge-stream-cache/gen.py DATA 1 250000 42 P` for P in 0..7). `ab.sh setup` loads the parts on the base server and copies them byte for byte to the fix server; `run` alternates `base` and the fix binary with `vertical_merge_max_parallel_columns` = N (`pN`), optionally with `vertical_merge_read_in_separate_thread` (`rN`), on pinned cores with a warm page cache: wall time, user/system CPU and peak memory from `system.part_log`, CPU of the whole server process from `/proc`, and the md5 of every file of every merged part; `summary` prints medians, min/max and the change. |
| `insert-sort-permute/` | melian/fix-insert-sort-permute | Block sort of an INSERT into a table `ORDER BY (org_id, event_time, id)` with the production `event` JSON column: `bench.sh` is the end-to-end HTTP `JSONEachRow` insert A/B on shuffled and pre-sorted files (one block and one partition per file), `verify.sh` compares every part file, `micro.sh` times single-threaded `INSERT ... SELECT` from a Memory table into the sorted table and into the same table `ORDER BY tuple()`, which isolates sort + permute, plus the `array_string_permute` perf-test queries. |

| `json-insert-parse/` | melian/fix-json-insert-parse | INSERT of JSON text into the production `event` JSON column the way Native clients send it: `gen.py ROWS SEED` writes JSONEachRow rows (arrays of objects among the paths that overflow into shared data), split into 40 files of 10500 rows and converted with `clickhouse local ... --output_format_native_write_json_as_string=1 -q "SELECT * FROM table FORMAT Native"`. `bench.sh` is the alternating HTTP `FORMAT Native` insert A/B (CPU us/row from `system.query_log`), `verify.sh` compares every part file and the table contents, `perf_test_query.sh` times the `json_parse_shared_data_arrays_of_objects` perf-test query with `clickhouse-local`. |
| `merge-stream-naming/` | melian/fix-merge-stream-naming | One `OPTIMIZE ... FINAL` merge per run with the production-shaped JSON column, three tables (`SCHEMA=`): 48 Compact parts x 20K rows of a table with 62 ordinary columns merged Vertically into a Wide part (`schema-cvw.sql`), 8 Wide parts x 300K rows merged Vertically (`schema-wide.sql`), 48 Compact parts merged Horizontally into a Compact part (`schema-ch.sql`). Same driver as `shared-data-gather/` (`load`, `run`, `prof`), 5 alternating base/fix runs on pinned cores: merge duration, user CPU and real time from `system.part_log`, md5 of every file of each merged part. |
| `merge-gather-copy/` | melian/fix-merge-gather-copy | One Vertical `OPTIMIZE ... FINAL` merge of 32 Wide parts x 250K rows (8M rows, 8.18 GiB) with the production-shaped JSON column, using the `shared-data-gather/` driver (`load BIN BIN 32 250000`, `run`): 5 alternating base/fix runs on pinned cores, merge duration and user CPU from `system.part_log`, md5 of every file of the merged part. `partcheck.sh` diffs `hash_of_all_files` of the merged parts of stateless tests 05484, 05512, 05536 and 05542 under four pairs of block limits. |
| `json-insert-parse-3/` | melian/fix-json-insert-parse-3 | The `json-insert-parse/` insert A/B with date inference off (as in the inserts it models), where JSON shared data gets arrays of objects whose objects get new `Dynamic` paths; `perf_test_query.sh` times the `json_parse_shared_data_wide_arrays_of_objects` perf-test query single-threaded in `clickhouse-local`. |
| `shared-data-merge-read/` | melian/fix-shared-data-merge-read | One Vertical `OPTIMIZE ... FINAL` merge of 8 parts of 500K rows with the production-like JSON column (~60 typed paths, `max_dynamic_paths=64`, ~250 untyped paths, 40-80 per row, arrays of objects), `advanced` shared data, `map_with_buckets` zero-level parts, rows of all parts interleaved. `load.sh` loads Wide source parts (32 buckets), `load_compact.sh` Compact ones (8 buckets); `ab.sh` / `ab_compact.sh` alternate base and fix on cores 0-7 and compare the merged parts byte for byte; `prof.sh` records a perf profile of one merge. Expects the binaries in `/work/bin`, works under `/work/sdr`. |
| `merge-writer-substreams/` | melian/fix-merge-writer-substreams | One Vertical `OPTIMIZE ... FINAL` merge of 8 Wide parts x 300K rows into a Wide part, with the production-shaped JSON column with 115 typed paths (`mkschema.py` adds 55 typed paths of `gen.py`'s pool to `schema-wide.sql`) and `advanced` shared data; `gen.py` takes `POOL_PATHS` (250 or 2000 untyped paths). `ab.sh load` generates and loads the parts, `ab.sh run` alternates base and fix on cores 0-7 (`bench.sh` from `merge-stream-naming/` with `PORT_OFFSET`, so two tables can be loaded side by side), merge duration and user CPU from `system.part_log`, md5 of every file of the merged parts. |
| `insert-json-traverse/` | melian/fix-insert-json-traverse | The `json-insert-parse-3/` insert A/B with the production `event` type with 115 typed paths (`gen.py` fills them; rows from 40 key templates in runs, 20-50 typed paths per template), 40 Native files of 16000 rows (`make_data.sh`), servers pinned to `CORES` and started with `setarch -R` so that address-space randomization does not move the results between server processes. `verify.sh` compares every part file and the table contents. `perf_test_query.sh` times the queries of `json_parse_varying_keys` and `json_parse_runs_of_same_keys` single-threaded in `clickhouse-local`. |

Usage of each driver is in the header comment of its script.
